# Identity, workspaces, and administration

## Product model

- A **user** is one human identity and may belong to several workspaces.
- A **workspace** is the security boundary. It owns domains, mailboxes, and mail data.
- A verified **domain** belongs to one workspace. A domain is never a permission by itself.
- A **mailbox** is an exact recipient address under one workspace domain.
- A user switches workspace in the UI. The server resolves the active workspace again on every request and checks current membership; a workspace id in a cookie or URL is never proof of access.
- A **platform administrator** manages workspace and identity metadata. This role grants no access to message bodies, attachments, exports, or send operations.

## Roles

Workspace roles are deliberately fixed in the first release:

| Role | Mail | Members | Domains and settings |
| --- | --- | --- | --- |
| Owner | read, write, send, classify, trash, export | manage | manage |
| Admin | read, write, send, classify, trash, export | manage | manage |
| Member | read, write, send, classify, trash, export | — | — |
| Viewer | read | — | — |

The `role_permissions` table is the source of grants. The client may hide unavailable actions, but every API operation must enforce its permission in the server. There are no user-defined roles in this first version.

The `owner` and `admin` roles also have `members.manage`, `domains.manage`, and `workspace.settings.manage` permission keys, but workspace-scoped management screens and API workflows are not implemented yet. The current user, domain, invitation, and mailbox-grant controls are platform-admin-only.

Platform administration uses the separate `platform_admins` table and a separate permission namespace. Workspace roles must never imply platform access. Sensitive administrative changes write an append-only audit event without message contents, credentials, invitation tokens, or other secrets.

## Account onboarding

Registration remains invite-only. A platform administrator can invite an exact email as a `member` or `viewer`; workspace-level invitation management and `admin` invitations are intentionally not enabled yet. Invitation tokens are random, single-use bearer credentials with a seven-day expiry; only their SHA-256 hashes are stored. One pending invitation is allowed per email and workspace, and D1 enforces a limit of ten invitations per platform administrator per hour inside the write transaction. The email follows the administrator's selected French or English UI locale. Acceptance checks the token, email, expiry, revocation, workspace status, account state, and existing membership before creating the account and membership atomically. Existing accounts must sign in as the invited identity first. Revoking an invitation is audited. Workspace membership does not grant mailbox access: an administrator must assign exact mailbox grants separately.

Authentication sessions contain only the stable user id and a session version. The active workspace is selected separately and validated against D1 on each request. Changing a password, suspending a user, or revoking access increments the session version. Nuxt Auth Utils is now installed as the session foundation. Local Nuxt development uses a host-only `courrier-dev-session` cookie name; production uses a distinct `courrier-session` name. Production must provide `NUXT_SESSION_PASSWORD` as a Worker secret before any login flow is enabled.

## Administrator area

The platform console shows workspaces, domain verification state, mailbox counts, user memberships, invitations, and audit history. It can invite members/viewers, revoke pending invitations, and manage exact mailbox grants for active members and active mailboxes; it does not show message contents. Invitation and grant changes are platform-admin-only for now and append audit events. A workspace owner's grant cannot be revoked through this interface. The console currently caps its access-management lists at 500 mailboxes, 500 active members, and 5,000 grants, and reports when those caps hide records. Workspace-scoped member administration and domain ownership verification remain future work.

## Current implementation boundary

The application has email/password login, logout, and password recovery endpoints using Nuxt Auth Utils sealed cookies and its scrypt password verifier. Sessions expire after seven days. Login and password recovery mutations require a same-origin `Origin`; login requires an active user with a password credential and either an active workspace membership or a platform-admin record. A reset link is sent only for an active account with a password credential; its random bearer token is one-use, expires after one hour, and only its SHA-256 hash is stored. Reset requests are rate-limited per normalized email and client IP using hashes; raw IP addresses are not stored. A successful reset increments the user's session version, invalidates all existing sessions, and appends a metadata-only account audit event. Failed login counts are keyed by SHA-256 hashes of normalized email plus Cloudflare client IP, with a second per-IP limit; raw IP addresses are not stored. These hashes are pseudonymous, not anonymization.

The initial owner was bootstrapped out of band as `jeremie@verbatims.cc` with owner membership in the legacy workspace and platform-administrator metadata. The `verbatims.cc` app domain remains `legacy_unverified`. Account identity alone grants no mailbox access: migration `0019` preserves existing active members' previous workspace-wide mail access with explicit grants for mailboxes mapped from canonical legacy recipient addresses and historical sender identities, including `courrier-test@verbatims.cc`, the configured sending identity. The migration does not create `jeremie@verbatims.cc` as a mailbox. Workspace-scoped administration and mailbox provisioning are not yet implemented. Newly created mailboxes and memberships receive no automatic grant; an administrator must assign access explicitly once those provisioning flows exist.

Worker-level Cloudflare Access is configured for previews only; no hostname Bypass application is currently used. Invited users reach Courrier's login, invitation, recovery, and admin flows on the public production hostname. There are no separate `/admin*` or `/api/admin*` Access applications. Courrier's Worker does not depend on Access identity headers: invitations, login, workspace selection, and mail access are controlled by application sessions and permissions. The auth-utils session endpoint is an explicit account route; all account endpoints validate their own session where needed. Every API response is marked private and non-cacheable. Profile avatars are stored under the account user id and require an account session. Mail APIs require a current account session, active workspace membership, a role permission, and an active grant to the relevant mailbox. Incoming messages are scoped to the exact envelope recipient; outgoing messages and standalone compose drafts are scoped to the sending mailbox. Reply drafts inherit access from their source message. Attachment bytes and raw MIME are served only after a scoped database lookup. Migration `0019` adds `mailbox_access_grants`; existing active members receive explicit grants for existing legacy mailboxes, while later memberships and mailboxes receive no implicit grant. The platform admin console can grant or revoke an existing member's exact mailbox grant; each change and its audit event are written in one D1 batch. Revocation preserves active owners' grants. Database triggers require each outgoing draft to point at a mailbox in its workspace. The admin overview omits invitation token hashes and audit `details_json`.

### Account MFA

All active members can optionally enroll a passkey from Settings. The first factor requires the account password; adding or removing a factor and rotating recovery codes requires a fresh MFA verification. When a member has a passkey or unused recovery code, password login creates an MFA-pending session: mailbox, account-management, and admin APIs remain blocked until `/mfa` accepts a passkey assertion or one-time recovery code. The member may explicitly turn MFA off from Settings; this deletes their factors, increments the session version to revoke every session, and requires a new password login. Members cannot manage another account's factors, and membership/workspace checks still apply.

Platform admins cannot disable MFA or remove their last passkey. Their administrative APIs still require a configured factor and a recent verification; production admin routes are not gated by Cloudflare Access and rely on these Courrier checks. Registering or removing a passkey increments the session version, revoking other sessions. Recovery-code rotation replaces prior codes after a fresh verification. Migration `0024` extends the WebAuthn challenge-purpose constraint for account login and account step-up while preserving existing challenge records and the expiry index.

The data model currently enforces tenant isolation through a domain-to-workspace mapping and exact mailbox grants, rather than a `mailbox_id` foreign key on every mail row. This preserves imported history while domains are being verified. It assumes each mail domain belongs to exactly one workspace; `workspace_domains.domain` is unique. Inbound routing now requires an exact active envelope-recipient mapping before storage, but legacy domains remain `legacy_unverified` until ownership verification is implemented. Because sender rules, blocked senders, manual merges, and private thread titles are still shared per domain, a user must have grants for every active mailbox in that domain before these domain-wide operations are visible or writable. A partial grant permits mailbox-scoped mail operations only. Sending remains constrained to the legacy `verbatims.cc` workspace because the configured Cloudflare Email binding currently permits only `courrier-test@verbatims.cc`. Worker-level Access is configured for previews only; production relies on Courrier authentication and authorization. Continue reviewing role, fresh-MFA, and recovery behavior before broadening account provisioning.

### Platform administrator factor recovery

An unused recovery code is a one-time MFA factor. If it is the final remaining factor, consuming it clears the configured-factor state: the current session is not considered MFA-verified for administration, and all platform-admin pages and APIs remain denied until a new factor is enrolled. The administrator can still sign in and open Settings; the first-passkey flow requires the account password. After the final code is accepted, the MFA page sends the administrator directly to Settings to enroll a replacement passkey. Password recovery does not remove or reset MFA factors.

If an administrator loses every passkey and recovery code, Courrier has no self-service MFA bypass. Another active platform administrator with a fresh MFA verification can now start a recovery from the platform console after typing the target's exact email address. In one D1 transaction, Courrier increments the target's session version, removes their passkeys, recovery codes, and pending WebAuthn challenges, and records a metadata-only `platform_admin.mfa_recovered_by_admin` event. The target's password, platform-admin role, workspace memberships, mailbox grants, and mail data stay unchanged. All of the target's sessions are invalidated; they can sign in with their password, but the console remains blocked until they configure and verify a new factor. The reset cannot be used on the acting administrator or on an inactive account, and a failed or stale authorization does not remove any factors.

If there is no other active administrator who can complete that flow, an authorized operator can use the guarded Wrangler command below against the exact D1 database as a break-glass procedure. It requires an incident reference and three exact interactive confirmations; invalidates every session before deleting factors and challenges; verifies the resulting state; and writes metadata-only `started` and `completed` audit events. It never reads or logs passwords, recovery-code hashes, passkey public keys, or challenges. The script sends each D1 statement in a separate Wrangler invocation, so if interrupted, the audit has a `started` event and the command must be rerun only after checking the target's current state.

The command syntax is `bun run account:recover-platform-admin-mfa -- --environment <canary|production> --email <admin-address> --incident <ticket-reference>`. The canary environment requires a separately seeded synthetic platform administrator; its standard synthetic account is a member and is deliberately not eligible. Use `--environment production` only during an approved, documented recovery incident. The command is intentionally interactive and refuses non-terminal use. The administrator can still sign in after recovery, but platform administration remains denied until a new passkey is registered from Settings with the account password and fresh recovery codes are stored separately. Password recovery does not reset MFA. Recovery by another active platform administrator is available in the console and covered by local integration checks. On 2026-10-17, the new canary drill also exercised the deployed Worker end to end with two synthetic administrators: the actor completed MFA step-up, the target's old session and factors were revoked, mail and admin access stayed denied until re-enrollment, and both accounts were removed afterward. The guarded operator command was exercised against the canary database, but neither recovery method has been used on a production account. Production recovery remains an untested break-glass path.

On 2026-10-16, the interactive recovery command was exercised against `courrier-canary-db` with a disposable synthetic platform administrator. The drill seeded placeholder passkey, recovery-code, and WebAuthn-challenge rows, then verified that recovery incremented the session version, removed all factors and pending challenges, invalidated the pre-recovery session, preserved password login, denied platform-admin APIs until re-enrollment, and left mailbox access unavailable. The password-confirmed passkey-registration options were available again after recovery. The synthetic account was deleted and the canary member baseline assertion passed; only the two metadata-only recovery audit events remain. This verifies the operator recovery path and post-reset authorization behavior, not a real WebAuthn ceremony or production recovery.

## Cloudflare Access readiness

The application no longer reads Cloudflare Access identity headers; a forged Access identity header does not authenticate a request. Email/password sessions, invite-only registration, explicit workspace membership, mailbox grants, same-origin mutation checks, and scoped API authorization are the application's access boundary for regular users. Password recovery uses one-hour single-use tokens and invalidates existing sessions. Local HTTP integration tests require all 62 protected API routes to reject anonymous requests; the current suite has 50 end-to-end checks, including a viewer matrix across all 10 non-admin read routes and 37 denied write/admin routes. Synthetic two-workspace fixtures also verify message search, mutations, attachments, inline draft attachments, drafts, reply drafts, outgoing sender authorization, bulk actions, and the generated export ZIP across mailbox grants. The new object-ID cases verify that hidden drafts, attachments, reply drafts, and messages cannot be changed by guessing their ids, and that a role with `mail.send` still cannot send from a mailbox it has not been granted. A viewer can read but cannot classify or export. Domain-wide sender rules and thread titles are hidden from a member with only a partial grant, while a member granted every active mailbox in the domain can see them. The suite also exercises invitations, session revocation, suspension/reactivation, explicit re-grants, a platform admin without mailbox access, MFA step-up, and recovery by a second active platform admin. This is broad regression coverage, not a proof that every authenticated route and state transition is exhaustively covered. A live local check on 2026-10-16 confirmed that revoking the platform-admin row clears the mounted admin console and returns the user to the inbox without a reload; the exact local row was restored immediately afterward. Production migration `0022` was confirmed in Cloudflare's D1 console on 2026-10-15. The user confirmed receiving the production password-reset email in the linked HEY inbox.

## Access canary

`wrangler.canary.jsonc` deploys a separate public Worker named `courrier-canary` at `https://courrier-canary.jerem-dev.workers.dev`. It is intended to test Courrier's own login and authorization boundary without changing the production Worker's Access rules. It has a dedicated D1 database (`courrier-canary-db`) and R2 buckets (`courrier-canary-mail-store`, `courrier-canary-mail-backup`); it has no production mail data, email-sending binding, or scheduled backup trigger. Its session cookie name is `courrier-canary-session`, and its `NUXT_SESSION_PASSWORD` is a separate Worker secret. Keep real mail, production identities, and production credentials out of the canary. The persistent browser test identity is the synthetic `canary.member@example.invalid` created by `bun run account:bootstrap-canary-member`; it receives a dedicated workspace, reserved `.invalid` domain, empty mailbox, and member role, with no platform-administrator access. `bun run account:test-canary-platform-admin` performs a temporary API smoke test using a random in-memory password and `canary.admin@example.invalid`; it creates no workspace membership, mailbox grant, or mail content, then removes the account and WebAuthn challenge. `bun run account:test-canary-admin-recovery` exercises recovery by a second administrator with two temporary `.invalid` accounts, synthetic factors, no workspace or mailbox grants, and no real WebAuthn ceremony. It verifies session invalidation, factor removal, re-enrollment eligibility, and denied access before re-enrollment, then removes both accounts and checks the original canary baseline. It retains only synthetic metadata-only audit events and requires interactive confirmation. Both scripts refuse non-terminal use and target the explicit canary configuration.

Use `npm run deploy:canary` to build, apply migrations to the D1 configured in `wrangler.canary.jsonc`, and deploy that Worker. This command must not be replaced with `npm run deploy`, which targets production. The canary is a separate, persistent Worker rather than a version URL: [Cloudflare version URLs reuse their Worker's configuration and resources](https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/), while an isolated deployment needs separate resource bindings. [Cloudflare Previews can isolate D1/R2 with separate resource IDs](https://developers.cloudflare.com/workers/previews/resources/), but remain subject to the relevant [Access policy](https://developers.cloudflare.com/workers/configuration/cloudflare-access/).
