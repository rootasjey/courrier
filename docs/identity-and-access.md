# Identity, workspaces, and administration

## Product model

- A **user** is one human identity and may belong to several workspaces.
- A **workspace** is the security boundary. It owns domains, mailboxes, and mail data.
- A verified **domain** belongs to one workspace. A domain is never a permission by itself.
- A **mailbox** is an exact recipient address under one workspace domain.
- A user switches workspace in the UI. The server resolves the active workspace again on every request and checks current membership; a workspace id in a cookie or URL is never proof of access.
- A **platform administrator** manages workspace and identity metadata. This role grants no access to message bodies, attachments, exports, or send operations.

## Roles

Workspace roles are deliberately fixed in the first release:

| Role | Mail | Members | Domains and settings |
| --- | --- | --- | --- |
| Owner | read, write, send, classify, trash, export | manage | manage |
| Admin | read, write, send, classify, trash, export | manage | manage |
| Member | read, write, send, classify, trash, export | — | — |
| Viewer | read | — | — |

The `role_permissions` table is the source of grants. The client may hide unavailable actions, but every API operation must enforce its permission in the server. There are no user-defined roles in this first version.

Platform administration uses the separate `platform_admins` table and a separate permission namespace. Workspace roles must never imply platform access. Sensitive administrative changes write an append-only audit event without message contents, credentials, invitation tokens, or other secrets.

## Account onboarding

Registration remains invite-only. A platform administrator can invite an exact email as a `member` or `viewer`; workspace-level invitation management and `admin` invitations are intentionally not enabled yet. Invitation tokens are random, single-use bearer credentials with a seven-day expiry; only their SHA-256 hashes are stored. One pending invitation is allowed per email and workspace, and D1 enforces a limit of ten invitations per platform administrator per hour inside the write transaction. The email follows the administrator's selected French or English UI locale. Acceptance checks the token, email, expiry, revocation, workspace status, account state, and existing membership before creating the account and membership atomically. Existing accounts must sign in as the invited identity first. Revoking an invitation is audited. Workspace membership does not grant mailbox access: an administrator must assign exact mailbox grants separately.

Authentication sessions contain only the stable user id and a session version. The active workspace is selected separately and validated against D1 on each request. Changing a password, suspending a user, or revoking access increments the session version. Nuxt Auth Utils is now installed as the session foundation. Local Nuxt development uses a host-only `courrier-dev-session` cookie name; production uses a distinct `courrier-session` name. Production must provide `NUXT_SESSION_PASSWORD` as a Worker secret before any login flow is enabled.

## Data isolation rollout

Migration `0016` introduced identity/workspace metadata and backfilled a single legacy workspace with unverified domains. Migration `0019` adds explicit mailbox grants and binds standalone compose drafts to a sender mailbox. Mail access now requires both the existing workspace permission and an active grant for the exact mailbox. Missing or revoked grants deny access.

Before broad invitation rollout, subsequent work must:

1. Keep Cloudflare Access on the administrator routes and Worker previews until authenticated and denied behavior has been verified in production and a recovery procedure is usable.
2. Keep the legacy domain's shared sender rules, blocks, thread merges, and private thread titles available only to members granted every active mailbox in that domain. Move these records to mailbox-level ownership before allowing partial-domain access to manage them independently.
3. Continue auditing every route for active user + active workspace membership + role permission + mailbox grant, including search, attachment content, raw MIME, export, sender rules, thread actions, draft actions, and sending.
4. Scope all SQL joins and R2 object access server-side. Never accept an object key or mailbox scope from the browser as authorization.
5. Resolve inbound mail from its exact envelope recipient to an active mailbox in an active workspace and non-suspended domain. Unknown, pending, or suspended recipients are rejected before message/attachment storage. The email-ingress trust path stays separate from browser sessions.
6. Verify in production that cross-workspace IDs, suspended users/memberships, revoked or expired invitation tokens, attachments, raw messages, search, exports, and send endpoints are denied as expected.
7. Deploy additive migrations and the complete scoped application while the administrator and preview Access barriers remain enabled. Do not remove those barriers until production verification of authenticated and denied requests is complete.

## Administrator area

The platform console shows workspaces, domain verification state, mailbox counts, user memberships, invitations, and audit history. It can invite members/viewers, revoke pending invitations, and manage exact mailbox grants for active members and active mailboxes; it does not show message contents. Invitation and grant changes are platform-admin-only for now and append audit events. A workspace owner's grant cannot be revoked through this interface. The console currently caps its access-management lists at 500 mailboxes, 500 active members, and 5,000 grants, and reports when those caps hide records. Workspace-scoped member administration and domain ownership verification remain future work.

## Current implementation boundary

The application has email/password login, logout, and password recovery endpoints using Nuxt Auth Utils sealed cookies and its scrypt password verifier. Sessions expire after seven days. Login and password recovery mutations require a same-origin `Origin`; login requires an active user with a password credential and either an active workspace membership or a platform-admin record. A reset link is sent only for an active account with a password credential; its random bearer token is one-use, expires after one hour, and only its SHA-256 hash is stored. Reset requests are rate-limited per normalized email and client IP using hashes; raw IP addresses are not stored. A successful reset increments the user's session version, invalidates all existing sessions, and appends a metadata-only account audit event. Failed login counts are keyed by SHA-256 hashes of normalized email plus Cloudflare client IP, with a second per-IP limit; raw IP addresses are not stored. These hashes are pseudonymous, not anonymization.

The initial owner was bootstrapped out of band as `jeremie@verbatims.cc` with owner membership in the legacy workspace and platform-administrator metadata. The `verbatims.cc` app domain remains `legacy_unverified`. Account identity alone grants no mailbox access: migration `0019` preserves existing active members' previous workspace-wide mail access with explicit grants for mailboxes mapped from canonical legacy recipient addresses and historical sender identities, including `courrier-test@verbatims.cc`, the configured sending identity. The migration does not create `jeremie@verbatims.cc` as a mailbox. Workspace-scoped administration and mailbox provisioning are not yet implemented. Newly created mailboxes and memberships receive no automatic grant; an administrator must assign access explicitly once those provisioning flows exist.

Cloudflare Access now has a public bypass on the canonical production Worker hostname so invited users can reach Courrier's own login, invitation, and recovery flows. More-specific Access applications protect `/admin*` and `/api/admin*` for Cloudflare account members, and the Worker-wide Access policy still protects preview URLs. Courrier's Worker does not depend on Access identity headers: invitations, login, workspace selection, and mail access are controlled by application sessions and permissions. The auth-utils session endpoint is an explicit account route; all account endpoints validate their own session where needed. Every API response is marked private and non-cacheable. Profile avatars are stored under the account user id and require an account session. Mail APIs require a current account session, active workspace membership, a role permission, and an active grant to the relevant mailbox. Incoming messages are scoped to the exact envelope recipient; outgoing messages and standalone compose drafts are scoped to the sending mailbox. Reply drafts inherit access from their source message. Attachment bytes and raw MIME are served only after a scoped database lookup. Migration `0019` adds `mailbox_access_grants`; existing active members receive explicit grants for existing legacy mailboxes, while later memberships and mailboxes receive no implicit grant. The platform admin console can grant or revoke an existing member's exact mailbox grant; each change and its audit event are written in one D1 batch. Revocation preserves active owners' grants. Database triggers require each outgoing draft to point at a mailbox in its workspace. The admin overview omits invitation token hashes and audit `details_json`.

The data model currently enforces tenant isolation through a domain-to-workspace mapping and exact mailbox grants, rather than a `mailbox_id` foreign key on every mail row. This preserves imported history while domains are being verified. It assumes each mail domain belongs to exactly one workspace; `workspace_domains.domain` is unique. Inbound routing now requires an exact active envelope-recipient mapping before storage, but legacy domains remain `legacy_unverified` until ownership verification is implemented. Because sender rules, blocked senders, manual merges, and private thread titles are still shared per domain, a user must have grants for every active mailbox in that domain before these domain-wide operations are visible or writable. A partial grant permits mailbox-scoped mail operations only. Sending remains constrained to the legacy `verbatims.cc` workspace because the configured Cloudflare Email binding currently permits only `courrier-test@verbatims.cc`. Before removing the remaining admin Access barrier, verify production recovery email delivery and authenticated and denied behavior for every API route; keep admin Access until those checks pass and the mandatory platform-admin MFA policy has been deployed and verified.

## Cloudflare Access readiness

The application no longer reads Cloudflare Access identity headers; a forged Access identity header does not authenticate a request. Email/password sessions, invite-only registration, explicit workspace membership, mailbox grants, same-origin mutation checks, and scoped API authorization are the application's access boundary for regular users. Password recovery uses one-hour single-use tokens and invalidates existing sessions. Local HTTP integration tests require all 50 protected API routes to reject anonymous requests; the current suite has 42 end-to-end checks, including a viewer matrix across all 10 non-admin read routes and 34 denied write/admin routes. Synthetic two-workspace fixtures also verify message search, mutations, attachments, inline draft attachments, drafts, reply drafts, outgoing sender authorization, bulk actions, and the generated export ZIP across mailbox grants. The new object-ID cases verify that hidden drafts, attachments, reply drafts, and messages cannot be changed by guessing their ids, and that a role with `mail.send` still cannot send from a mailbox it has not been granted. A viewer can read but cannot classify or export. Domain-wide sender rules and thread titles are hidden from a member with only a partial grant, while a member granted every active mailbox in the domain can see them. The suite also exercises invitations, session revocation, suspension/reactivation, explicit re-grants, and admin MFA setup and step-up. This is broad regression coverage, not a proof that every authenticated route and state transition is exhaustively covered. Production migration `0022` was confirmed in Cloudflare's D1 console on 2026-10-15; the recovery email flow still needs an end-to-end production delivery check.

The production Worker currently uses a Bypass policy for `courrier.jerem-dev.workers.dev/*`, with more-specific Access applications for `/admin*` and `/api/admin*` restricted to Cloudflare account members. Worker-level Access remains enabled for previews. Anonymous production requests now reach the app login, while mail APIs deny them; admin page and API requests still redirect to Access. A production member session can read its permitted mailbox scope and cannot access platform administration. Recovery email delivery has not yet been verified end to end in production, and the local cross-workspace/export scenarios have not been replayed against production data. Courrier implements passkey and recovery-code MFA for platform administrators. The current source now requires a configured factor and a fresh step-up for admin routes and APIs, including the initial password-confirmed passkey-enrollment path; this enforcement change still needs deployment and canary verification before it can be relied on in production. Keep Access on admin pages and APIs until that verification is complete. Fully removing Access is unnecessary for normal users; before exposing platform administration outside Access, verify the enforced MFA policy and repeat the production denial and recovery checks. Keep Access on Worker previews.

## Access canary

`wrangler.canary.jsonc` deploys a separate public Worker named `courrier-canary` at `https://courrier-canary.jerem-dev.workers.dev`. It is intended to test Courrier's own login and authorization boundary without changing the production Worker's Access rules. It has a dedicated D1 database (`courrier-canary-db`) and R2 buckets (`courrier-canary-mail-store`, `courrier-canary-mail-backup`); it has no production mail data, email-sending binding, or scheduled backup trigger. Its session cookie name is `courrier-canary-session`, and its `NUXT_SESSION_PASSWORD` is a separate Worker secret. Keep real mail, production identities, and production credentials out of the canary. The only supported test identity is the synthetic `canary.member@example.invalid` created by `bun run account:bootstrap-canary-member`; it receives a dedicated workspace, reserved `.invalid` domain, empty mailbox, and member role, with no platform-administrator access.

Use `npm run deploy:canary` to build, apply migrations to the D1 configured in `wrangler.canary.jsonc`, and deploy that Worker. This command must not be replaced with `npm run deploy`, which targets production. The canary is a separate, persistent Worker rather than a version URL: [Cloudflare version URLs reuse their Worker's configuration and resources](https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/), while an isolated deployment needs separate resource bindings. [Cloudflare Previews can isolate D1/R2 with separate resource IDs](https://developers.cloudflare.com/workers/previews/resources/), but remain subject to the relevant [Access policy](https://developers.cloudflare.com/workers/configuration/cloudflare-access/).

The anonymous browser check passed: the login page renders without an Access interstitial, `/api/account/session`, `/api/messages`, and `/api/admin/overview` all return `401`, and forged `Cf-Access-*` identity headers do not grant access. The synthetic-member bootstrap is a separate operator-run step; authenticated member behavior remains unverified until that account is created and exercised in the browser. This canary result does not authorize removing production Access: keep the production admin routes and Worker previews protected until the production recovery and authenticated/denied checks above are complete, and retain Access for platform administration until the mandatory MFA policy is deployed and verified.
